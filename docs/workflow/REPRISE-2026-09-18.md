## Ce qu’il faut récupérer

Dépôt du jeu : https://github.com/lucasdasilvammi/lcg-app
Branche de travail : `codex/lcg-v1-cleanup`.
Point de départ du code audité : `7bcad37` sur main.

Cette branche transporte les changements locaux préexistants dans un commit de
sauvegarde distinct, l’audit, les journaux, les décisions et le skill. Aucun
correctif applicatif de l’audit n’a été commencé le 17 septembre.

Le chat précédent n’est pas nécessaire. Ne pas supposer que les paramètres Codex,
les autorisations locales, les dépendances ou les variables d’environnement sont
transportés par Git.

### Premier clone sur la nouvelle machine

Depuis le dossier où ranger le projet, avec Git installé :

```sh
git clone --branch codex/lcg-v1-cleanup https://github.com/lucasdasilvammi/lcg-app.git lcg-app
cd lcg-app
```

Ouvrir ensuite ce dossier comme projet dans Codex. Sélectionner le modèle et le
niveau de raisonnement souhaités dans cette installation. Le prompt ci-dessous
peut ensuite lancer la session.

### Si le projet existe déjà sur cette machine

Vérifier `git status` avant de changer de branche. Si des changements locaux sont
présents, les préserver ; ne pas utiliser reset --hard, clean ou un checkout forcé.
Puis récupérer `origin` et rejoindre la branche :

```sh
git fetch origin
```

Si elle n’existe pas encore localement :

```sh
git switch --track origin/codex/lcg-v1-cleanup
```

Si elle existe déjà :

```sh
git switch codex/lcg-v1-cleanup
git pull --ff-only origin codex/lcg-v1-cleanup
```

Ne pas pull main pour récupérer cette session : la sauvegarde est sur la branche
de travail. En cas de divergence locale, inspecter les commits et préserver le
travail avant de résoudre le conflit.

## Contexte essentiel

Lucas valide l’ordre de nettoyage mais veut préserver le jeu actuel : mêmes
parcours, apparence et règles. Il souhaite des petits commits sur la branche de
travail, puis un gros patch sur main seulement une fois l’ensemble validé. Les
étapes 0, 1 et 2 sont autorisées pour la prochaine session ; les étapes suivantes
ne doivent pas être commencées automatiquement.

Le rôle de l’hôte doit pouvoir passer à un autre joueur si son téléphone se
coupe. Le nouvel hôte doit pouvoir réinviter l’ancien, en conservant son joueur,
ses scores et l’état de partie. La correction ne doit pas supprimer cette
fonctionnalité : elle doit séparer les droits gérés par le serveur des secrets
personnels de reconnexion. Expliquer à Lucas le fonctionnement réellement retenu
après implémentation et tests.

Le moteur principal est `server.js` ; `server/index.js` est encore lancé par les
tests permanents. Le client est React/Vite/Tailwind avec état Socket.IO.

Défauts confirmés lors de l’audit sur serveur local fictif :

- l’état diffusé expose les sessionToken des autres joueurs ; réutiliser le jeton
  de l’hôte permet de reprendre sa place ;
- plusieurs commandes ne contrôlent pas correctement le rôle/la phase ; une même
  résolution ajoute plusieurs fois les points ;
- `resolve_interaction(null)` peut arrêter le processus ;
- le test de catalogue attend 158 questions alors que le JSON courant en a 342.

Baseline mesurée : lint client sans erreur/avertissement ; build du jeu
réussi ; Jest 53 tests réussis et 1 échec d’effectif ; cinq intégrations rejouées
contre le principal dans une copie temporaire : 5/5 ; scénarios Socket.IO 11/11 ;
collisions bonus 7/7 ; worklog 2/2. Les scénarios ne prouvent pas le déroulement
d’une partie complète. Aucune validation exhaustive sur téléphone ni sur les
services déployés n’a été effectuée.

Les anciens scripts de mesure dans tmp/poc-audit ne sont pas transférés. Le
rapport contient les preuves, sources et commandes ; les tests permanents sont
dans le dépôt. Reconstituer les régressions ciblées à l’étape 1.

## Installation et périmètre de sauvegarde

L’audit a utilisé Node 22.19.0/npm 10.9.3. Les anciens manifests annoncent encore
Node 18/npm 8 : incohérence connue, ne pas changer toutes les versions pendant
les étapes 0–2. Utiliser un runtime compatible et vérifier les contraintes.
Les installations sont séparées : `npm ci`, `npm --prefix client ci` et
`npm --prefix server ci` préparent le jeu et Jest, après inspection des scripts.
Ne pas lancer le build racine pour installer : il réinstalle implicitement.
Pour les builds d’audit, choisir une sortie ignorée :
`npm --prefix client run build -- --outDir ../tmp/poc-audit/client-build`.
Le build normal réécrit build/, qui est encore suivi par Git.

- Les fichiers source et docs nécessaires aux étapes 0–2 sont transférés.
- Question Studio / LCG Studio est entièrement hors périmètre, y compris les
  versions présentes ailleurs sur les machines. Ne rien consulter, modifier,
  tester, cloner ou synchroniser dans cet outil. Le jeu se reprend seul.
- `docs/books/` contient 290 fichiers locaux (~775 Mio), principalement des
  photos de livres. Ils restent sur la première machine, hors du push. Transfert
  séparé nécessaire pour un travail éditorial futur ; inutiles pour ce nettoyage.
- Les node_modules, caches, fichiers temporaires et secrets .env ne voyagent pas
  avec Git. Aucun secret de production n’est nécessaire aux tests locaux du jeu.
